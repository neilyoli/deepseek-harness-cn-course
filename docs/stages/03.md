# Stage 3：Cordis 核心机制

## 毕业能力映射

【教学模型】直接服务于：**架构理解、Service Plugin、Hook Plugin、HMR / inject / event 排障**。

## 依赖顺序

【源码事实】官方 Cordis tutorial 的当前教学顺序与本阶段一致：

```text
Plugin
↓
Lifecycle / Fiber
↓
Effect
↓
Service / inject
↓
Events
↓
Config
↓
Composition / Isolation / HMR
```

## Plugin instance 与 Fiber

【源码事实】`ctx.plugin(plugin)` 返回 Fiber；Fiber 是 live plugin instance 的生命周期句柄。

典型状态：

```text
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
                   ↘ FAILED
```

【工程解释】“Plugin 代码文件”与“正在某个 Context 中运行的一次 plugin instance”不是同一件事。Fiber 才回答“这个实例现在是否 active、依赖什么、何时 dispose”。

## Effect 为什么必须可逆

【源码事实】`ctx.effect(() => disposer)` 把外部资源纳入当前 Fiber lifetime；`ctx.on`、child plugin、service registration、Harness registries 的 register 通常也都是 Cordis-managed effects。

【工程解释】HMR、provider 消失、parent unload 都会让 plugin 在你意料之外的时刻撤销。如果注册是不可逆的，热更新必然积累 ghost listener / duplicate tool / leaked timer。

注意：

【源码事实】多个 async disposer 启动顺序按逆注册方向，但可并发运行；如果必须严格 teardown A 再 B，把顺序放进同一个 disposer 并 `await`。

## Service 与 inject：不仅是普通 DI

【源码事实】Service 在 Context 下用稳定 key 发布。Consumer 声明 required `inject` 后：

```text
Provider absent  → Consumer PENDING
Provider appears → Consumer loads
Provider disappears after active → Consumer unloads
Provider returns → Consumer can load again
```

【工程解释】所以 `inject` 同时表达依赖和生命周期条件；它不是只在构造时取一次对象的 DI container。

## Event mode

【源码事实】Cordis 当前核心模式：

| mode | 语义 |
|---|---|
| `emit` | 同步广播，不等待异步返回 |
| `parallel` | await 全部 listener，并行 |
| `serial` | 顺序 await，首个有效决策可终止 |
| `bail` | 同步顺序决策 |
| `waterfall` | around-middleware；listener 决定是否调用 `next()` |

【工程解释】waterfall 适合 runtime extension point，因为它允许：

```text
transform before
→ await next()
→ inspect/transform after
```

也允许策略短路 default behavior。

### Debug Lab：忘记 `next()`

注册一个只想观察 `tools/pre-execute` 的 waterfall listener，却不调用 `next()`。观察 downstream policy / default path 被吞掉。修复成：

```ts
ctx.on('tools/pre-execute', async (exec, next) => {
  ctx.logger('lab').info(exec.name)
  return next()
})
```

具体 event signature 必须以 Event Catalog 为准，不要照抄示意参数。

## Config

【源码事实】Loader 在 `apply` 前用 plugin 导出的 `Config` runtime schema 验证 row config。`!!js` 配置表达式在 injections 就绪后针对 plugin context 求值。

## Composition 与 Isolation

【源码事实】config row `id` 是 diff/HMR 的稳定身份。官方 Cordis tutorial 特别指出：没有显式 id 的 entry 在每次 config read 会生成新 id，因此 config 文件变化会导致它 remount。

【源码事实】group + isolate 可以给一组 provider/consumer 一个独立 service realm。

【工程解释】Isolation 解决“同一 Service key 需要多个相互隔离实例，但 consumer 仍按同一 ctx key 编程”的问题。

## 必做故障

- missing inject；
- duplicate registration；
- listener 不 cleanup；
- waterfall 忘记 `next()`；
- 无 id row 导致 HMR 重挂载；
- isolate 内外错误读取 Service。

## 验收

给出一个 plugin，能够**提前预测**：

```text
load
→ ACTIVE
→ required provider disappears
→ consumer dispose
→ provider returns
→ consumer reload
→ HMR config changes
→ old effects cleanup + new activation
```

并能指出每一步由 Fiber / inject / Effect / Loader 中谁拥有。
