【源码事实】`core/scope` 不是 Cordis Service；它提供库原语。

## Agent 是当前 ScopeKey

【源码事实】`ReactLoopAgent` 构造：

```ts
this.scope = createScope(loopCtx, this)
this.ctx = this.scope.ctx.extend({ agent: this })
```

`ScopeKey` 类型只要求 opaque object identity；scope primitive 不读取 Agent 字段。

## Scoped registry 的核心规则

【源码事实】`ScopedLayers` 有一个 eager global layer 与按需 exact-scope layers。读取不创建 layer；注册时把“可见性 layer”与“Cordis effect ownership”绑定在同一个 registration context 上。

【源码事实】以 `ctx.systemPrompt.section()` 为例：scoped section 会 shadow 同名 global section；tools 也有 own scoped registrations/restrictions。

【工程解释】scope 解决两个问题：

1. **谁能看见这条 registration？**
2. **谁 dispose 时这条 registration 必须消失？**

如果只用一个 `Map<agentId,...>` 做过滤，很容易忘 lifecycle owner。

## Service isolation ≠ Agent scope

【工程解释】Cordis isolation 解决同名 Service realm；Agent scope 解决共享 Harness Services 之上的 per-agent registration visibility。两个 Agent 通常仍共享 `ctx.llm`、`ctx.tools` service object，但 `ctx.tools` 内部根据 scope layer 解析可见 registrations。

## Lab：两个 Agent

【教学模型】通过正常 Agent factory 创建 Agent A/B。

1. 用 root ctx 注册 global tool `global_ping`。
2. 用 `agentA.ctx` 注册 `a_only`。
3. 用 `agentB.ctx` 注册 `b_only`。
4. 分别 assemble system prompt / tool schemas。
5. 断言 A 看 global+a，不看 b；B 看 global+b，不看 a。
6. dispose A 的 scope/Agent；确认 global 与 b 仍在，a 消失。

## Event scope

【源码事实】部分 event declaration 的 receiver 使用 `Scoped<T>`；`scopeTarget(base,key)` 构造纯 routing carrier，真实 subject 仍在 payload / explicit arg。查 Event Catalog 时要同时看 event name 和 receiver type。

## 故障：两个 Agent 能力串线

【教学模型】排查顺序：

```text
registration 是 root ctx 还是 agent.ctx？
↓
registry 是否支持 scoped layer？
↓
assembly/execution 是否带正确 ScopeKey / Agent initiator？
↓
event listener 是否 scope-filtered？
↓
dispose 是否走同一 owned Context？
```
