# Stage 11：Session Persistence

## 毕业能力映射

【教学模型】直接服务于：**Resume / crash recovery 调试、Capability seam、Core 修改**。

## 先分两层

```text
core/session
  owns: in-memory Session + append-only event log
        ↓ live session/event notification
SessionPersistence
  owns: durability seam + batching/flush/load/inspect/prepare
        ↓
JSONL / SQLite providers
```

【源码事实】`ctx.sessionPersistence` 是 abstract capability seam；它持久化**同一个 SessionEvent vocabulary**，没有另一套 parallel persisted-event type。

## 当前后端

【源码事实】当前 subsystem 文档明确列出：

- `dsh-session-persistence-jsonl`：每 session 的 append-only logical JSONL，默认用 checksummed concatenated Zstandard frames 或 raw lines 配置；
- `dsh-session-persistence-sqlite`：`node:sqlite` backend，物理结构不同，但返回完整 logical event stream。

【版本敏感】文档 prose 早处有“three interchangeable providers”措辞，而当前列举段落显示两种 shipping backend；本教程不据此猜第三个 provider。遇到这类数量冲突，查 package group 与 capability graph 后再下结论。

## `session/event` 与 batching

【源码事实】`session/event` 是同步 notification；persistence listener 把 event 放入 per-session controller，不阻塞 producer。第一个 pending event 开始固定 batching window，后续 events 加入但不重置 deadline。

## `session/flush`

【源码事实】`session/flush` 取消 batching wait 并 drain 到 quiescence；loop/相关 policy 用它作为 durability ordering/error-observation checkpoint。disposal 也执行 final drain。

【工程解释】“append 到内存 log”与“已经 durable”是两个不同完成条件。读 resume bug 时必须问现在处于哪一层。

## Crash recovery

【源码事实】cold persisted log 若存在 `turn/start` 但没有 matching `turn/end`：

- 不截断已 durable 的大 turn；
- recovery 在逻辑上关闭 orphan turn；
- 添加 synthetic `turn/end { reason: { kind: 'interrupted' } }`；
- `interrupted` 是 loop 本身不会正常 emit 的恢复原因。

【源码事实】live session 与 cold session 不同：live authoritative session 若仍 open turn，不能随便注入 synthetic close。

## inspect / prepare / load

【源码事实】当前 persistence seam 区分：

- `inspect(id)`：不可变逻辑视图，不 publish；cold inspection 可在内存平衡 interrupted turn 而不写修复；
- `prepare(id)`：保留 unpublished exact Session + provider state，供 setup/publication/rollback；
- `load(id)`：按 persistence contract 取得逻辑 session，并处理 recovery/durability 语义。

具体签名必须读 `docs/subsystems/persistence.md` 生成 API 段与 source。

## Lab A：Flush / Reload

【教学模型】用测试 backend 或当前默认 persistence：

1. 创建 Session；
2. append 一组 events；
3. 观察 append 后立即读取 backend 与 flush 后读取的差异；
4. `session.flush()` / 对应 service checkpoint；
5. dispose；
6. load/inspect；
7. 对比 seq、header、event payload。

## Lab B：Interrupted Turn

【教学模型】优先在 test fixture 中构造 cold log：

```text
turn/start
step/start
user/message
assistant/chunk...
<process crash, no close>
```

加载后验证 synthetic `turn/end(interrupted)`，并确认之前 events 没有被 truncate。

## 故障定位树

```text
Resume 不正确
├─ in-memory Session projection wrong? → core/session
├─ events never durable? → session/event batching / flush
├─ backend decode/corruption? → provider
├─ open turn repair wrong? → persistence recovery
├─ wrong agent preset/composition? → SessionHeader + agent-presets
└─ model history wrong? → deriveMessages / surface semantics
```

## 验收

画出：

```text
process crash
↓
durable prefix
↓
cold load / validation
↓
interrupted turn repair
↓
prepared Session
↓
agent resume
```

并指出每一步的 owner package。不能把 `SessionPersistence` 说成 `core/session` 的“数据库实现细节”。
